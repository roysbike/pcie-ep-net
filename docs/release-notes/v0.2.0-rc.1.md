## Summary

openmiop **v0.2.0-rc.1**: Ethernet (`omi0`) between Mixtile Blade 3 boards
over the Mixtile Cluster Box PCIe fabric, now interrupt-driven and
multiqueue (OpenMIOP protocol v4 framing, new features negotiated per
connection).

* **RSS / multiqueue:** 4 queue pairs, both eDMA channels in parallel, one
  NAPI context and one RX interrupt per queue on its own A76 core.
  ~8 Gbit/s between two blades with several flows, 22 Gbit/s for four
  blades sending at once (rc.2: 11.7).
* **RX interrupts** (GIC ITS doorbell) and **TX completion interrupts**
  instead of polling threads: `omi-ctl` ~6 % -> ~1 %, the TX thread
  ~92 % -> ~15 % of a core.
* Works with v0.1 blades and the existing BMC helper.

Changes: [CHANGELOG.md](https://github.com/roysbike/pcie-ep-net/blob/v0.2.0-rc.1/CHANGELOG.md).
Design: [docs/v0.2-design.md](https://github.com/roysbike/pcie-ep-net/blob/v0.2.0-rc.1/docs/v0.2-design.md).

Interrupt-driven RX needs Linux 6.10 or newer (Talos 1.14: 6.18). On the
Mixtile Debian 12 vendor kernel (6.1) the module builds without it and
polls RX as in v0.1; multiqueue and TX interrupts work there.

## Installation

### Debian / Ubuntu

```sh
sha256sum -c --ignore-missing SHA256SUMS
sudo apt install ./openmiop-dkms_0.2.0-rc.1_all.deb
echo 10.20.0.<last octet of the management address>/24 | sudo tee /etc/openmiop.addr
sudo reboot
```

### Talos

`talosctl upgrade` to the mixtile-talos v0.2.0-rc.1 installer, one node at
a time. A staged upgrade (`--stage`) avoids hanging in pod unmounts.

## Upgrade

* Mixed v0.1/v0.2 members work: a pair where both run v0.2 uses 4 queues
  and doorbells; any other pair uses one ring and polling, as in v0.1.
* Module parameters: `queues=` (1, 2 or 4), `rx_doorbell=0` (poll RX),
  `tx_irq=0` (poll TX).

## Verification

```sh
dmesg | grep openmiop        # "RX doorbell: 15 buses x 4 queues", "peer M up, 4 queues, doorbell"
ethtool -l omi0              # Combined: 4
ethtool -S omi0 | grep -E 'rx_q[0-3]_packets|doorbell|irq_lost'
grep -E 'omi-rx|openmiop-edma' /proc/interrupts
```

## Tested

Lab Cluster Box: four Blade 3 on Talos v1.14.2 with this driver, BMC on
ClusterBox firmware v0.1.0-rc.3, MTU 9000, Gen3 x2 links, a loaded
Cozystack cluster on top.

| Test | Result |
| --- | --- |
| Every ordered pair, 4 TCP streams | 7.9-8.4 Gbit/s (4.3-4.7 when the flows hashed onto one or two queues) |
| Four senders at once (ring), 4 streams each | 22.2 Gbit/s total (rc.2: 11.7) |
| One TCP stream | 4.1-4.8 Gbit/s (one flow uses one queue) |
| Driver errors / drops | none |
| CPU | `omi-ctl` ~1 %, TX threads ~13-18 % per channel under load |
| Mixed versions, rolling upgrades, BMC reboot, hard resets of all blades | all peers reconnect, 4 queues + doorbell |

Not tested on hardware: Debian/Ubuntu with v0.2 (CI builds and installs
the DKMS package for Debian 12/13 and Ubuntu 22.04/24.04 kernels).

## Known limitations

* One flow is limited to one queue and one eDMA channel (~4.7 Gbit/s).
* No checksum/GSO offload yet.
* A BMC reboot (e.g. a firmware update) takes the fabric down for
  minutes; storage replication over `omi0` (DRBD 9.3.4 on the lab
  cluster) needed node reboots afterwards. Plan BMC updates as
  maintenance.
