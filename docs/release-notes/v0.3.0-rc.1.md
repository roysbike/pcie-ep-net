## Summary

openmiop **v0.3.0-rc.1**: the Cluster Box no longer has to read the
blades, and the blades no longer need the Cluster Box to talk to each
other.

* **Push mode.** If the Cluster Box BMC (MT7620A, the PCIe root complex)
  had a read of a blade's memory in flight while that blade's link
  dropped, the root complex stopped answering until the BMC rebooted.
  v0.2.0-rc.2 avoided that for announced events (reboot, `nodectl`
  release); a blade that crashed or lost power could still hit it. Now
  the blade writes its state into the BMC's memory and the BMC only
  writes into blades. The BMC side is a kernel module, `omi-rc`, shipped
  in the ClusterBox firmware.
* **Blades keep the fabric up on their own.** After a Cluster Box
  reboot (which resets every blade link) the blades enable their BAR
  themselves and reconnect P2P ~12 s after the link reset, before the
  BMC side runs again.
* **Stalled peer recovery.** A peer that stays stalled for 2 s right
  after it connected is connected again instead of being dropped for
  good (seen after blade reboots).

Wire format between blades is still protocol v4: v0.2 and v0.3 blades
talk to each other. Changes:
[CHANGELOG.md](https://github.com/roysbike/pcie-ep-net/blob/v0.3.0-rc.1/CHANGELOG.md),
design: [docs/push-mode.md](https://github.com/roysbike/pcie-ep-net/blob/v0.3.0-rc.1/docs/push-mode.md).

## Upgrade order

1. **Blades first**, one at a time. A v0.3 blade works with the old
   userspace helper; the BMC needs nothing new yet.
2. **Then the BMC** (firmware v0.1.0-rc.5). `omi-rc` leaves blades
   without push mode alone, so every blade must run v0.3 before the BMC
   switches to the module.

`omi-rc` and `openmiop-rc` must not run together. To try the module on
older firmware with the same kernel, stop the helper, `insmod omi-rc.ko`,
then give `omi0` its address (10.20.0.1/24, MTU 9000) and restart
`dnsmasq` and `sysntpd`, which bind to it. Back: `rmmod omi_rc`,
`/etc/init.d/openmiop start`.

## Verification

```sh
# BMC
dmesg | grep omi0     # "node N active: <mac>, BAR ..., epoch ..., doorbell" per blade
# blade
dmesg | grep openmiop # "RC push mode: state at ...", "gateway v2: ring at ..."
ethtool -S omi0 | grep ctl_stall_reconnects
```

## Tested

Lab Cluster Box: four Blade 3 on Talos v1.14.2 (6.18.54) with this
driver, BMC on ClusterBox firmware v0.1.0-rc.4.

| Test | Result |
| --- | --- |
| Cluster Box reboot, userspace helper (3 times) | blades reconnect P2P by themselves in ~12 s |
| `omi-rc` loaded instead of the helper, four blades under a loaded cluster | all active in 1.6 s, no P2P interruption |
| Blade reset by `nodectl` 2.0-3 with `omi-rc` | released, then link down 27 ms later; blade active again 13 s after the reset, peers reconnected, node Ready in ~2 min |
| Blade upgrade with a peer stalled after connect | `peer N stalled, connecting again`, back in 2 s |

Throughput was not measured again; the data path is the same as in
v0.2.0-rc.1.

## Known limitations

* `omi-rc` does not re-enumerate the bridge windows: a blade whose BAR
  got no address is only logged (the userspace helper does this).
* A blade that crashes or loses power with no release is now harmless
  to the root complex by design, but not tested on purpose yet.
* A Cluster Box reboot still resets every blade link for the length of
  its boot. On Blade 3 that also resets the M.2 NVMe (shared PERST#);
  mixtile-talos v0.3.0-rc.1 brings it back.
* Why a rebooted blade gives no credit in its first 100 ms is open; the
  stall reconnect covers it.
* One flow uses one queue: ~4.7 Gbit/s per flow.
