## Summary

openmiop **v0.3.0-rc.2** fixes the Cluster Box module `omi-rc`: loaded at
boot, it left the blades alone for ~5 minutes. The blade driver and the
userspace helper are unchanged from
[v0.3.0-rc.1](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.3.0-rc.1).

* **The problem.** On the 32-bit BMC, jiffies starts 300 s before it
  wraps. Two deadlines in `omi-rc` (first link sample, rescan) were 0
  and only passed at that wrap. With ClusterBox firmware v0.1.0-rc.5 the
  module loads at ~45 s of uptime and activated the blades only at
  ~300 s. Blade-to-blade traffic was fine (blades reconnect without the
  BMC), but the BMC gateway was down meanwhile: the blades' default
  route, DNS and NTP through 10.20.0.1 timed out.
* **The fix.** Both deadlines start when the module loads.

Changes: [CHANGELOG.md](https://github.com/roysbike/pcie-ep-net/blob/v0.3.0-rc.2/CHANGELOG.md).

## Verification

After a Cluster Box boot:

```sh
dmesg | grep omi0    # "node N active" a few seconds after "openmiop root complex, push mode"
```

## Tested

The fix compiles clean (W=1, Linux 5.15 MIPS). The delay was seen on the
lab Cluster Box after flashing ClusterBox firmware v0.1.0-rc.5 on
2026-10-12. Verification on hardware needs a Cluster Box boot with this
module, i.e. ClusterBox firmware v0.1.0-rc.6; not done at tag time.

## Known limitations

As in [v0.3.0-rc.1](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.3.0-rc.1):
`omi-rc` does not re-enumerate bridge windows; a crash or power cut of a
blade without a release is not tested on purpose; one flow uses one
queue (~4.7 Gbit/s).
