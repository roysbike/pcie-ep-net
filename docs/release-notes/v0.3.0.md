## Summary

openmiop **v0.3.0** is the first stable release of push mode: the
Cluster Box no longer reads the blades, and the blades no longer need
the Cluster Box to talk to each other. Same code as
[v0.3.0-rc.2](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.3.0-rc.2);
this release adds the hardware test of the whole stack.

* **Push mode.** If the Cluster Box BMC (MT7620A, the PCIe root complex)
  had a read of a blade's memory in flight while that blade's link
  dropped, the root complex stopped answering until the BMC rebooted.
  Now the blade writes its state into the BMC's memory and the BMC only
  writes into blades. The BMC side is a kernel module, `omi-rc`, shipped
  in ClusterBox firmware v0.1.0 and loaded at boot.
* **Blades keep the fabric up on their own.** After a Cluster Box
  reboot (which resets every blade link) the blades enable their BAR
  themselves and reconnect P2P ~12 s after the link reset, before the
  BMC side runs again.
* **Stalled peer recovery.** A peer that stays stalled for 2 s right
  after it connected is connected again instead of being dropped.
* **`omi-rc` activates the blades right after boot** (fixed in rc.2; in
  rc.1 it waited ~5 min for a 32-bit jiffies wrap).

Wire format between blades is still protocol v4: v0.2 and v0.3 blades
talk to each other. Changes since v0.2:
[CHANGELOG.md](https://github.com/roysbike/pcie-ep-net/blob/v0.3.0/CHANGELOG.md),
design: [docs/push-mode.md](https://github.com/roysbike/pcie-ep-net/blob/v0.3.0/docs/push-mode.md).

## Upgrade order

1. **Blades first**, one at a time. A v0.3 blade works with the old
   userspace helper; the BMC needs nothing new yet.
2. **Then the BMC** (firmware v0.1.0). `omi-rc` leaves blades without
   push mode alone, so every blade must run v0.3 before the BMC
   switches to the module.

From the 0.3.0 release candidates: nothing changes on the blades
(same driver since rc.1). A BMC on firmware rc.5 should move to v0.1.0
(rc.6 has the same `omi-rc` as v0.1.0).

## Verification

```sh
# BMC
dmesg | grep omi0     # "node N active: <mac>, BAR ..., epoch ..., doorbell" per blade, seconds after "push mode"
# blade
dmesg | grep openmiop # "RC push mode: state at ...", "gateway v2: ring at ..."
```

## Tested

Lab Cluster Box: four Blade 3 on Talos v1.14.2 (6.18.54) with this
driver (mixtile-talos v0.3.0-rc.1), BMC on ClusterBox firmware
v0.1.0-rc.6 (same `omi-rc`), MTU 9000, Gen3 x2, a loaded Cozystack
cluster on top.

| Test | Result |
| --- | --- |
| Cluster Box boot, `omi-rc` loaded by the firmware init | loaded at 45.1 s, all four blades active at 46.7 s; blade DNS via the BMC back the same second; NVMe live on all blades, etcd 3/3, DRBD clean |
| Blade reset by `nodectl` 2.0-3 | released, link down 32 ms later, active again 14.5 s after the reset, node Ready in ~46 s |
| Every ordered pair, 1 TCP stream | 4.3-5.1 Gbit/s, 0 retransmits |
| One pair, 4 streams / bidirectional | 8.1 Gbit/s / 6.9 + 7.0 Gbit/s |
| Four senders at once (ring), 4 streams each | 25.0 Gbit/s total (v0.2.0-rc.1: 22.2) |
| Cluster Box reboot with the helper (rc.1, 3 times) | blades reconnect P2P by themselves in ~12 s |

## Known limitations

* `omi-rc` does not re-enumerate the bridge windows: a blade whose BAR
  got no address is only logged (the userspace helper does this). Not
  seen with the lab blades.
* A blade that crashes or loses power with no release is harmless to
  the root complex by design, but not tested on purpose.
* A Cluster Box reboot still resets every blade link for the length of
  its boot. On Blade 3 that also resets the M.2 NVMe (shared PERST#);
  mixtile-talos v0.3.0 brings it back.
* One flow uses one queue: ~4.7 Gbit/s per flow.
