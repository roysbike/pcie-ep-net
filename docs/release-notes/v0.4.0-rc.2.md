## Summary

openmiop **v0.4.0-rc.2** fixes two blade-side bugs found while
benchmarking the v0.4.0-rc.1 gateway. Under long blade -> LAN uploads
(Cluster Box CPU at 99 %) a blade could lose the gateway for good: no
LAN, internet, DNS or NTP over omi0 until `omi-rc` was reloaded.
Traffic between blades (Kubernetes, etcd, DRBD) was not affected.

* **False peer stalls.** A blade called a peer stalled when its queue
  looked full and the credit did not move between two reads of one
  control-thread pass. The TX thread picks up credit too, so under load
  a healthy peer looked stuck; after 100 ms its frames were dropped,
  and a peer that had already read everything never returned credit
  again. Progress now counts against the credit seen at the last pass,
  and an empty ring counts as alive. This also hit P2P peers: a blade
  on rc.1 logged hundreds of stalls and reconnects under load.
* **Gateway v2 reconnect deadlock.** 2 s after such a stall the blade
  reconnected to the Cluster Box (peer 7) like to a blade: it wrote a
  blade connect line into the BMC's ring area and came back up with
  head 0 against the BMC's old tail, so the ring looked full forever.
  The blade no longer reconnects to the BMC that way and continues at
  the BMC's credit.
* **`omi-rc`:** when it resyncs a blade's ring it writes the new credit
  at once (this also frees a blade still on rc.1), logs a warning and
  counts `rx_fifo_errors`.

Changes: [CHANGELOG.md](https://github.com/roysbike/pcie-ep-net/blob/v0.4.0-rc.2/CHANGELOG.md).

## Verification

```sh
# blade, after a long upload through the Cluster Box
ethtool -S omi0 | grep -E 'ctl_peer_stalls|ctl_stall_reconnects|tx_dropped_late'   # 0 or rare
dmesg | grep 'peer 7'        # no "stalled, connecting again"
# BMC
cat /sys/class/net/omi0/statistics/rx_fifo_errors   # 0
```

## Tested

Lab Cluster Box, 2026-10-13. Stress round: 3 parallel 300 MB blade ->
LAN uploads plus a 300 MB LAN -> blade download through the BMC (NAT,
flow offloading), BMC CPU at 99 %; then ping the BMC.

| Blade driver / `omi-rc` | Result |
| --- | --- |
| rc.1 / rc.1 (.133) | gateway lost in round 4 (and in a single benchmark run) |
| reconnect fix only / rc.2 `omi-rc` (.108) | gateway lost in round 1-2 (false stall, no reconnect) |
| **rc.2 / rc.2 `omi-rc` (.108)** | 21 rounds, 0 stalls, 0 reconnects, 0 late drops, 0 eDMA errors |

The last 15 rounds ran during 240 s of P2P load from the same blade
(iperf3 -P 4 to another blade, 8.7 Gbit/s).

## Known limitations

- As in [v0.4.0-rc.1](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.4.0-rc.1):
  the BMC CPU limits the gateway (~200 Mbit/s each way); `omi-rc` does
  not re-enumerate bridge windows; one flow uses one queue
  (~4.7 Gbit/s).
