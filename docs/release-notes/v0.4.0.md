## Summary

openmiop **v0.4.0** is the stable release of OpenMIOP Stack v0.4.0. It
makes the Cluster Box gateway (LAN and internet to the blades) about twice
as fast and fixes peer stalls under load. Same code as
[v0.4.0-rc.2](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.4.0-rc.2).

* **Gateway pull.** Until v0.3 the BMC wrote every frame for a blade into
  the blade's PCIe BAR with its CPU, one uncached 32-bit write per word.
  Now the BMC copies the frame into its own RAM and the blade reads it
  with an eDMA read channel; the BMC writes only a 16-byte slot header.
  Negotiated (`OMI_HDR_GW_PULL`): v0.3.x blades and BMCs keep working.
* **No more false peer stalls.** Under load a blade could take a healthy
  peer for stuck (progress was measured between two reads of one pass
  while the TX thread also picks up credit), drop its frames and later
  reconnect. Towards the Cluster Box that reconnect could lock the
  gateway ring for good (no LAN, internet, DNS, NTP over omi0 until
  `omi-rc` was reloaded).

Changes: [CHANGELOG.md](https://github.com/roysbike/pcie-ep-net/blob/v0.4.0/CHANGELOG.md).

## Verification

```sh
# BMC
dmesg | grep omi0                                   # "node N active: ..., doorbell, gateway pull"
cat /sys/class/net/omi0/statistics/rx_fifo_errors   # 0 (2 per blade reconnect are harmless)
# blade
ethtool -S omi0 | grep -E 'rx_gw_pulls|rx_gw_pull_errors|ctl_peer_stalls|ctl_stall_reconnects'
```

## Tested

Lab Cluster Box, 2026-10-13: four Blade 3 on mixtile-talos v0.4.0-rc.2
(this driver), BMC on ClusterBox firmware v0.2.0-rc.2 (this `omi-rc`).

| Test | Result |
| --- | --- |
| LAN -> blade through the BMC (NAT, flow offloading) | 193-198 Mbit/s (v0.3: 92) |
| Blade -> LAN | 228-238 Mbit/s |
| BMC -> blade, iperf3 on the BMC | 189-204 Mbit/s (v0.3: 130) |
| Internet -> blade | 126-175 Mbit/s |
| Gateway stress: 3 parallel 300 MB uploads + 300 MB download per round, BMC CPU 99 % | 21 rounds on .108 (15 of them during 8.7 Gbit/s P2P load), 6 on .133, 6 with the release `omi-rc`: gateway up, 0 stalls, 0 reconnects, 0 late drops, 0 eDMA errors (v0.4.0-rc.1: gateway lost in 1-4 rounds) |
| BMC reboot (firmware v0.2.0-rc.2 flash) | all 4 blades active with gateway pull 47 s after power-on, NVMe live, etcd and DRBD reconnected |

## Known limitations

- The BMC CPU (one MIPS core) is the gateway limit: ~200 Mbit/s to a
  blade, ~230-270 Mbit/s from a blade. Zero-copy on the BMC is a later
  step.
- When a blade reconnects, `omi-rc` may log two harmless `resync`
  warnings (stale head from the previous connection).
- A BMC reboot drops every blade link for the length of its boot. With
  DRBD 9.3.4 on top this can force-demote a Primary if a Secondary holds
  stale out-of-sync bits towards it
  ([LINBIT/drbd#153](https://github.com/LINBIT/drbd/issues/153)); check
  `drbdsetup status --statistics` (`out-of-sync:` 0) before rebooting the
  BMC.
- As before: `omi-rc` does not re-enumerate bridge windows; one flow uses
  one queue (~4.7 Gbit/s).
