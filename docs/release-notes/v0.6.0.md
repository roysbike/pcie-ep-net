## Summary

openmiop **v0.6.0** makes blade-to-blade traffic faster: one TCP flow
between two v0.6 blades reaches 7.8-8.0 Gbit/s (5.0-5.5 with v0.5.0).

* **TX on the big cores.** The TX threads and the eDMA done interrupts
  now run on the biggest cores, the Cortex-A76 (CPUs 4-7) on RK3588.
  Before, the scheduler put them on the A55 cores as often as not, and
  one flow was 5.0-5.5 Gbit/s. The driver logs
  `TX threads and eDMA interrupts on CPUs 4-7`; parameter `tx_cpus`
  overrides the choice.
* **Checksum offload between blades** (`OMI_FEAT_CSUM`). `omi0` announces
  `NETIF_F_HW_CSUM`. A frame for a single blade that offered the feature
  keeps its partial TCP/UDP checksum, as on virtio-net, and the receiver
  hands it on as `CHECKSUM_PARTIAL`. If the frame leaves that host again,
  for example routed to the BMC gateway, the kernel completes the
  checksum. Checksumming was ~11 % of the sender's CPU time. The payload
  crosses only PCIe links (LCRC, replayed on error) and DRAM.

  Frames to the BMC, broadcasts and floods, and peers without the
  feature still carry a full checksum. `peer N up, ..., checksum offload`
  in the log shows a pair that uses it. Parameter `p2p_csum=0` turns it
  off.
* Protocol v4 framing is unchanged. The feature is negotiated for each
  connection, so v0.6 blades work with v0.5 and older blades during a
  rolling upgrade.
* `omi-rc` and the BMC helper are the same as in v0.5.2; the BMC needs no
  update.

Changes: [CHANGELOG.md](https://github.com/roysbike/pcie-ep-net/blob/v0.6.0/CHANGELOG.md).

## Verification

On a blade:

```sh
dmesg | grep openmiop    # "TX threads and eDMA interrupts on CPUs 4-7"
                         # "peer N up, 4 queues, doorbell, checksum offload"
ethtool -k omi0 | grep tx-checksum-ip-generic   # on
grep -E 'Tcp:|Udp:' /proc/net/snmp             # InCsumErrors stays 0
```

## Tested

Lab Cluster Box, 2026-10-19/20, Talos v1.14.2 with a loaded Cozystack
cluster:
* .108 and .201 on a mixtile-talos test image with this driver
  (openmiop 0.5.3-dev.1, the code of this release without the tx_build
  hardening for peers that come back older);
* .133 and .204 on v0.5.0 with the TX threads pinned to the A76 by hand;
* BMC on the OpenWrt 25.12 development firmware.

| Path, 10 s iperf3 | v0.5.0 | v0.6.0 pair |
| --- | --- | --- |
| One TCP flow | 5.0-5.5 Gbit/s (6.5-7.2 pinned by hand) | 7.82-7.98 Gbit/s, 0 retransmits |
| Four TCP flows | 10.0-10.5 Gbit/s (pinned by hand) | 11.1-11.3 Gbit/s |
| Pod to pod (Kube-OVN Geneve), 1 / 4 flows | | 5.3-5.6 / 8.6 Gbit/s |

Integrity: payload hashed on both ends; every transfer below was
identical and `InCsumErrors` stayed 0 on all blades and on the
workstation.

* 4 GiB TCP over IPv4 and IPv6 in both directions, between v0.6 blades
  and between v0.6 and v0.5.
* 200 000 UDP datagrams of 24-8900 bytes over IPv4 and IPv6, each with
  its own hash (losses only from receive buffer overflow,
  `Udp:RcvbufErrors`).
* 2 GiB pod to pod and pod to ClusterIP over Kube-OVN Geneve. There the
  partial checksum is that of the inner TCP header.
* 512 MiB HTTP downloads from a workstation through the BMC gateway and a
  NodePort on .201 to a pod on .108. The reply crosses .108 -> .201 with a
  partial checksum, and .201 completes it before the gateway; the
  workstation's NIC verifies it.
* Restart of a peer: when .201 rebooted, .108 renegotiated the offload
  when .201 came back.

One hour soak (2026-10-20 06:48-07:49 UTC): iperf3 in both directions
between .108 and .201 all the time, and integrity loops of 1 GiB each
running alongside. All results:

| Loop | Result |
| --- | --- |
| v0.6 <-> v0.6 host to host | 349/349 identical |
| pod -> ClusterIP -> pod (Geneve) | 210/210 |
| v0.6 -> v0.5 / v0.5 -> v0.6 | 237 / 339 identical (the test pods restarted once; the transfers cut off then are not counted) |
| workstation <- BMC gateway <- NodePort <- pod, 512 MiB | 97/97 |

No new driver or kernel messages on the blades or the BMC; error
counters unchanged; DRBD out-of-sync stayed 0.

## Known limitations

- One flow still uses one queue and one eDMA channel; four flows reach
  ~11 Gbit/s between two blades.
- No TSO/GSO: the stack segments to the 9000-byte MTU.
- Traffic to the BMC gateway is computed in software as before; the BMC
  CPU (one MIPS core) limits it to ~200-280 Mbit/s.
